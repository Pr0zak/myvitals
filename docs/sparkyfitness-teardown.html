SparkyFitness Teardown

Read of CodeWithCJ/SparkyFitness at HEAD — Node/TS server, React web, Expo mobile, Python Garmin sidecar — against the myvitals source, subsystem by subsystem. It is a breadth machine: 22 integrations, 33 locales, nutrition·cycle·meds·pregnancy. myvitals is a depth machine. Almost nothing here is worth copying as an implementation; several things are worth copying as a shape.

The one finding that changes plans

SparkyFitness integrates the Google Health API v4 — https://health.googleapis.com/v4/users/me/dataTypes — a server-to-server REST API with its own OAuth scopes. It pulls Pixel Watch data without a phone app in the loop at all, and its data-type list includes oxygen-saturation and daily-sleep-temperature-derivations: the exact two streams that are currently dead on your PW3/PW4 through Health Connect. Everything else in this document is an improvement. This one is a second, independent path to your own watch data.

Question 1How it handles workouts, and what data it pulls in

The model is a denormalised ~80-column exercise_entries table with a normalised exercise_entry_sets child. A "workout" is not an entity — it is an exercise_preset_entries session-header row that child entries point at, hung on a bare entry_date. There is no start timestamp, no status machine, no seed, no recovery context.

What it does not have, at all

No generation. No progression. No autoregulation. Grepping the whole repo for deload/progression turns up a nutrition coaching prompt and nothing else. workout_plan_templates is a literal weekly calendar that, on activation, eagerly materialises ~260 diary sessions — thousands of INSERTs — synchronously inside one HTTP request. Nothing reads HRV, sleep or readiness before prescribing anything. It stores training_load, tss_score and aerobic_training_effect as inert provider telemetry and never consumes them.

Set against analytics/strength.py:generate_plan(), adaptive split selection, MEV/MAV auditing, micro-loader rounding and six AI coach surfaces, myvitals is not in the same category. Do not port anything from their planner.

The three things it genuinely has that myvitals does not

1 — Energy cost of lifting exists. CalorieCalculationService.ts is crude (a 7×3 MET table, a bare ×0.9 for female, −0.5%/5yrs over 30, all flagged as unscientific in its own comments) but it produces a number. myvitals produces none: there is no kcal, calorie or MET string anywhere in api/workout/strength.py or analytics/strength.py, and Activities.vue emits kcal: null for every synthesised strength row. Every lifting session is invisible in your daily energy story.

myvitals can beat their approach outright here. They guess from a MET lookup because they have no HR stream. You own a continuous per-minute HR series across exactly the session window and can integrate Keytel over it. Return kcal_method ∈ {hr, met, none} to the UI and null rather than inventing a 70 kg default — the fabricated default is precisely their failure mode.

2 — Free-form logging is the default. A session with workout_preset_id = NULL is a first-class citizen. myvitals has no route that adds an exercise to a session: there is POST /workout-exercises/{id}/swap (1:1, 409s once a set exists), DELETE /workouts/{id} and DELETE /sets/{id} — and nothing else. Three extra sets of curls done in the moment have nowhere to go, so they never reach tonnage, the volume audit, PR detection or any AI payload.

3 — Activity telemetry is modelled properly. exercise_entries carries normalized power, TSS, intensity factor, HR recovery at 1 min, ground contact time, vertical oscillation, stride length, elevation gain/loss, weather, gear — plus side tables exercise_entry_hr_zones, exercise_entry_laps, exercise_entry_gps_points, and a per-provider raw JSONB blob. And daily_health_metrics holds acute_training_load, chronic_training_load, acwr_ratio, training_readiness_score, recovery_time_hours and race predictions.

One transferable idea, and it is a good one. resolveAssumedSetValues: a three-tier per-field placeholder cascade — previous session's same-index set, then the plan captured at live-start, then the row above — tiered separately for warm-up vs working so a light warm-up can never seed a working target. Sets are created empty and the plan is a grey suggestion that becomes data only when performed. myvitals' two clients currently disagree on exactly this: StrengthToday.vue seeds from the flat slot target with rating null, while StrengthTodayScreen.kt inherits the last logged set and pre-selects rating 4.

Question 2How it pulls data from Strava

Bring-your-own-app OAuth, polled hourly. The user pastes their own Strava Client ID and Secret into external_data_providers.app_id/app_key (AES-256-GCM encrypted per row). The server builds the authorize URL with scope read,activity:read_all,profile:read_all, exchanges the code, stores the rotated refresh token and an expires_at, and getValidAccessToken refreshes lazily at a 5-minute margin.

The generic provider framework underneath it

This is the part worth studying. One table holds every credential for all 22 providers, with an encrypted triple (ciphertext, iv, tag) per secret and columns for token_expires_at, last_sync_at, sync_frequency, external_user_id, oauth_state. A companion lookup table external_provider_types stores each provider's required_fields[], field_labels jsonb, categories[] and an is_strictly_private flag — and the settings UI renders its credential form and its validation from that data. Registering a new provider's config surface is one INSERT.

is_strictly_private sits on the provider type, not the row. One boolean excludes every wearable from family sharing, enforced identically in the repository WHERE clauses and in the Postgres RLS policy. Food providers stay shareable; anything holding an OAuth token never is.

Where their Strava is worse than yours

  • No webhooks anywhere in the repo. Strava's push Events API is unused; a finished ride takes up to an hour.
  • The scheduled window is today only while the manual button defaults to 7 days — an activity uploaded after local midnight for the previous day is never picked up by cron. Silent data loss.
  • sync_frequency='daily' is a lie: every cron block is '0 * * * *', gated only on !== 'manual'.
  • No 429 handling. Fixed 500 ms sleeps, no header inspection, no backoff. Strava's 100-per-15-min limit is hit around 200 activities and the failures are swallowed.
  • No persisted auth-failure state. No last_error column; a week of failing syncs only console.errors and the sole user-visible signal is a "Last Sync" timestamp that stopped advancing. This is the exact bug myvitals already fixed in v0.7.319.
  • The CSRF state round-trip is decorative — state = userId and the callback destructures only {code}.
What this comparison actually surfaced in myvitals. Their sync is one funnel; yours is not. maybe_complete_cardio_day is called from integrations/strava.py:262 (the retired OAuth path) and from Concept2 — but not from strava_web.upsert_activity_from_fit, which is the only Strava path that actually runs. Cardio-day auto-completion is dead for every ride you sync. Separately, _link_activity_to_trail has exactly one caller (the manual POST /trails/link-activities), and upsert_activity_from_fit's ON CONFLICT DO UPDATE writes avg_hr, max_hr and polyline unconditionally — so a re-sync where FIT parsing fails silently nulls good HR and GPS on an existing row.

The Garmin sidecar pattern

Garmin auth is hostile (unofficial, MFA), so it lives in a separate Python FastAPI service wrapping garth — with a genuinely elegant custody rule: the sidecar never persists a token. Node passes the decrypted session dump on every request and re-encrypts any new_tokens handed back mid-sync, so the sidecar can be restarted or run untrusted. Backfills are chunked at ≤7 days with a token refresh per chunk, so a long import cannot be killed by an expiry halfway through. myvitals' backend is already Python, so you would not need the sidecar — but the ≤7-day chunk-with-refresh pattern is directly applicable to Strava bulk backfill.

Question 3How it syncs with Google for Pixel Watch data

Two completely independent paths. Understanding that they are separate is the whole answer.

Path A — Health Connect via the phone (same shape as yours)

An Expo/React-Native app using react-native-health-connect. A single registry (src/HealthMetrics.ts) declares ~50 metrics with recordType, permissions[], readKind (cumulative-day | min-max-avg-day | raw), aggregation strategy and background frequency; one platform-neutral engine drives Android and iOS behind a HealthReadProvider interface.

Three ideas here are better than myvitals':

  • Cross-source dedupe is delegated to the OS. Cumulative metrics go through aggregateGroupByPeriod with no dataOriginFilter, so Health Connect applies the user's own app-priority list and the totals match what the HC UI shows. A test asserts the filter is absent. This is strictly better than reimplementing source selection — provided the priority list is trustworthy, which is the caveat that keeps pick_canonical_steps_source justified.
  • Timezone-change day attribution. Two pageSize:1 edge probes read each record's startZoneOffset; when they diverge from the device zone it binary-searches the transition day and re-buckets anchored at the records' midnights. Guarded against dateline jumps and UTC-stamping exporters. Given how many times the local-day bug has recurred in myvitals, this is the mature version of that problem.
  • Resumable, checkpointed history backfill. A per-metric earliest-sample probe from the 1970 epoch finds the true floor rather than guessing "1 year". The checkpoint freezes the metric set so a resume is coherent, the cursor rounds up so the seam day is re-imported rather than skipped, and every abnormal stop (quota, device-locked, app-inactive, server-changed) is a named resumable outcome with user-facing copy and a pace-based ETA.

Their weaknesses are instructive too: no offline write buffer at all (myvitals' Room buffer is better), steps stored as one GREATEST()-merged integer with no source column so an inflated day can never be corrected downward, and most vitals — HRV, SpO2, VO2max, resting HR — dumped into a generic custom_measurements catch-all as TEXT.

Path B — the Google Health API, server-to-server, no phone

This is the find. SparkyFitnessServer/integrations/googlehealth/ does OAuth against Google directly and reads from https://health.googleapis.com/v4/users/me/dataTypes, with per-domain scopes:

ScopeCovers
googlehealth.activity_and_fitness.readonlysteps, distance, floors, exercise, activity-level, active-zone-minutes, total-calories
googlehealth.health_metrics_and_measurements.readonlyheart-rate, daily-resting-heart-rate, daily-heart-rate-variability, oxygen-saturation, daily-respiratory-rate, daily-vo2-max, core-body-temperature, weight, body-fat, height
googlehealth.sleep.readonlysleep, daily-sleep-temperature-derivations
googlehealth.profile.readonly · settings.readonly · nutrition.readonlyprofile, settings, hydration-log

Reads come in three shapes: a date-filtered dataPoints range query for instantaneous types, an unfiltered paged list for static types like height, and a dataPoints:dailyRollUp call for daily aggregates. Daily-aggregate types are filtered client-side because the API will not filter them server-side.

Why this matters more than anything else here. Your CLAUDE.md records two live upstream defects: the PW3/PW4 firmware bug where the watch reports "no app is requesting permissions" for SpO2 and skin temperature, and the removal of minute-level skin temperature from Google Health exports. Both are Health Connect on-device problems. The cloud API exposes oxygen-saturation and daily-sleep-temperature-derivations as first-class data types. It is also a full redundancy path: today the phone is a single point of failure for every stream you own, and this needs no phone, no HC grant, and no app upgrade to survive.

Caveat, stated plainly: I read their client code, not Google's terms. Verify the API's availability in your region, its quota, and whether Fitbit-sourced Pixel Watch data actually populates those types for your account before building on it. That verification is the first task, not an afterthought.

Question 4How it handles charts and reports

One page — pages/Reports/Reports.tsx — with eight pill tabs: Nutrients, Measurements, Fasting, Exercise, Sleep, Stress, Medications, Table. recharts pinned at 3.8.0, plus react-grid-layout for a drag-resize widget grid and leaflet for GPS maps. Tab, startDate and endDate all live in URL search params, so any report view is bookmarkable. Default range is 14 days; presets are 7/14/30/90/180/365 plus a calendar range.

Worth taking

  • URL-addressable report state. Cheap, and it makes every "go look at X" link in the app land on the right view.
  • Comparison periods — previous-period and last-year, rendered as a 0.6-opacity second series behind the primary.
  • Goal overlays as dashed ${key}_goal lines merged per-date, plus HRV mean±1SD as a ReferenceArea.
  • Evenly-spaced SQL downsampling in pure window functions — row_number() and count() OVER (), then modulo — guaranteeing ≤ maxPoints while always keeping the first row. It has a unit test that asserts the SQL text.
  • Refusing to fabricate. HR-zone seconds come only from recorded rows; empty zones stay 0, with the reasoning in-code: "a zero reads as nothing recorded, an estimate is indistinguishable from a real reading."
  • DISTINCT ON (exercise_name) ORDER BY … estimated_one_rm DESC, entry_date ASC for PRs, with a comment explaining that independent MAX() aggregates report a set that was never actually performed.
  • Per-tab error boundaries, and a grid error boundary that degrades to a stacked view without deleting the saved layout.

Where it falls apart — and where myvitals already wins

Aggregation is hybrid and inconsistent. aggregationLevel (daily/weekly/monthly) is sent as a query param and never read server-side — the browser downloads every daily row and buckets it. GET /reports is one monolithic payload fetched regardless of which tab is open, and the whole page blocks on a single boolean ANDing six queries. Both comparison modes produce a disjoint date window while the client matches on identical entry_date, so the comparison bars are essentially always zero. Export is client-side CSV Blobs of whatever the open tab happened to fetch; the only "PDF" is window.print().

And mobile chart parity is close to nil: three chart components total, a different stack (victory-native + Skia), no Reports screen at all. myvitals' enforced parity plus server-side analytics is the better architecture by a wide margin — the lesson is what to add, not how to build it.

What this surfaced in myvitals. analytics/cardio.py:time_in_zone_for_activity and cardio_summary are complete, correct, time-weighted with a 30 s gap cap — and reachable only from integrations/claude.py. They have no HTTP route. Meanwhile ActivityDetail.vue defines its own zoneFor() and counts samples per zone rather than seconds, so an activity with irregular HR sampling shows a distribution that disagrees with the number the AI cardio coach quotes back. The phone shows no zones at all.

Question 6How it uses Free Exercise DB

Nothing is bundled. The catalog is fetched live from GitHub at request time, across three upstreams: search hits api.github.com/repos/yuhonas/free-exercise-db/contents/dist/exercises.json and re-downloads the entire ~1.5 MB array on every cache miss; detail hits raw.githubusercontent.com/…/exercises/<Id>.json; images resolve to raw GitHub URLs. A fourth call goes straight from the browser to the dataset's schema.json.

Caching is one NodeCache at 1 hour, keyed on query + filters + limit + offset — so paging re-downloads the whole array. Unauthenticated GitHub REST is 60 requests/hour/IP, and a 403 is caught and returned as {exercises: [], totalCount: 0}, i.e. rate-limited renders as "no results". No timeout, no ETag, no backoff, no offline fallback. myvitals bundling the JSON plus ~24 MB of images is unambiguously the better call.

The one idea here that is better than yours, and it is important. They adopt the dataset's schema.json enums as the app's canonical internal taxonomy, then translate every other provider into it. wgerNameMapping.ts is commented "Maps SparkyFitness muscle names to wger muscle names" — the keys are literally free-exercise-db's primaryMuscles enum. garminExerciseMapper.ts spells out the reasoning: Garmin's category enum has no muscle field, so it is hand-mapped to FEDB names "so Garmin-created exercises render on the body map and filter correctly alongside everything else." One vocabulary, one body map, one filter. The filter chips are read from schema.json at runtime so they can never drift from the data.
Why that matters for myvitals right now — verified counts. The catalog is 201 + 74 = 275 rows. MUSCLE_VOLUME_TARGETS has 14 keys and contains none of quads (5 rows), core (6), neck (2) or flexibility (15). weekly_muscle_volume keys on the raw catalog string and emits only keys present in the targets dict — so Cossack Squat, Lateral Lunge, Walking Lunge, Dumbbell Step-Up, Dumbbell Sumo Squat and all six Pilates rows credit exactly zero sets, while ~40 secondary-credit tokens (hips, hip_flexors, adductors, groin, spine, upper_back, rear_delts, serratus, brachialis) evaporate through the same path. Separately, SPLIT_SLOTS and FINISHER_PATTERNS between them name 11 movement patterns, so the 10 rows tagged tricep_isolation / bicep_isolation / chest_isolation / lateral_squat can never be selected by the generator at all. An alias map already exists twice — on both clients, for icons only. Display normalises; the maths does not. That wrong number is on the audit card and feeds muscle_need() for adaptive split selection.

Two smaller things they get right: an SSRF-hardened image downloader (redirect cap of 5 with the guard re-run per hop, content-type allowlist, 10 MB streaming limit that unlinks the partial file, md5(url) in the filename), and a self-healing image route that treats the local uploads directory as a cache and re-derives from upstream on a miss, so wiping the volume is non-destructive. Attribution, though, is prose-only — the Unlicense is never named anywhere, which is worth noting since myvitals ships the same dataset.

Question 7Its UI, and what myvitals could take

Two clients with different information architectures and nothing enforcing parity: web home is the Diary, mobile home is a Dashboard. Web customisation is a server-persisted drag-resize grid; mobile customisation is five booleans in local AsyncStorage. myvitals' scripts/parity_check.py has no counterpart here — that gate is a real advantage you already hold.

Day navigation — the single strongest UI idea in the codebase

DayNavigator is a pill [‹][📅 date][›] with a "Today" chip that appears only when off-today and ?date= URL sync. The part worth copying verbatim is that getDateRelationToToday() returns past | today | future, and that value tints the entire nav chrome — desktop tab strip and mobile bottom bar both get a coloured border plus a 10%-opacity overlay from --date-past / --date-future tokens. You cannot forget you are looking at a different day. Mobile mirrors it with fling gestures and tab-re-tap to return to today.

Directly relevant to a recurring myvitals bug class. Your CLAUDE.md records the UTC-vs-local day bug landing three separate times — /summary/today, then /summary/readiness in v0.7.369. Making "you are not looking at today" impossible to miss is worth more in myvitals than it is in Sparky. And the foundation is already built: analytics/tiles.py:tile_stats(db, day, …) and analytics/events.py:day_events(db, day, tz) are both fully day-parameterised while /summary/tiles takes no parameter at all. Meanwhile DayNav.kt exists on four phone screens and grepping frontend/src for DayNav|selectedDate|prevDay returns nothing — an unregistered parity break.

The widget grid

One generic WidgetGrid (react-grid-layout) over a page_key-keyed jsonb table user_dashboard_layouts(layout, hidden), with a server-side allow-list of valid page keys. The piece most home-grown dashboards get wrong and this one gets right is reconcileLayouts(saved, currentKeys, defaults): widget keys are derived from user entities, so the saved layout is reconciled against the current key set on every load — stale entries dropped, new widgets appended at maxY, existing placements preserved. Creating or deleting an entity never corrupts the grid.

Other patterns worth lifting

  • Deep-linkable settings — ?tab= selects the pill group, ?section= also pre-expands the accordion item, so any "go configure X" link lands on the exact open panel.
  • Permission tooltips that describe the negative space — each family-access checkbox states what is blocked. That is what makes a permission model trustworthy.
  • lazyWithChunkRecovery — catches stale-chunk import failures after a deploy, reloads once behind a 30 s sessionStorage guard, and returns a never-resolving promise so React renders "Updating…" instead of a stack trace.
  • Onboarding pacing — 250 ms auto-advance after a single-choice tap, a deliberate 1000 ms "Preparing your personalised plan…" beat, and a conditional step whose inclusion is latched on first resolve so Back cannot skip a step you just filled.
  • Fail-closed privacy — discreetMode = isLoading || isError || settings?.discreet_mode, so a sensitive label can never flash during load or on a failed fetch.
  • Headless reconcilers mounted outside visibility gates, so hiding a card never silently disables its notifications.
And a shipped dead end this comparison found in myvitals. Settings.vue's activeTab is assigned exactly once, from ?tab= — there is no in-page tab bar. Under the classic shell SideNav.vue supplies the twelve links, but theme.ts defaults themeChoice to 'neon', and under neon App.vue renders NeonNav instead, so SideNav never mounts. You.vue then offers exactly four settings pills. Eight of twelve panes — access, ai, tools, imports, trails, fasting, ha, concept2 — are reachable only by typing a URL, so on the default theme a fresh visitor cannot reach AI configuration, historical imports, or Home Assistant setup at all.

Not in their docsThe sleep-science engine

Undocumented, unmentioned in the README, and the most sophisticated deterministic analytics in the repo. services/sleepScienceService.ts (887 lines) exposes seven endpoints: /sleep-debt, /chronotype, /mctq-stats, /daily-need, /energy-curve, /calculate-baseline, /data-sufficiency.

  • It derives your sleep need instead of asking you to type it. MCTQ over a 90-day window, requiring ≥8 free days and ≥20 work days, clamped to 6.0–10.0 h with a 0.15 strain factor. Work-vs-free days are classified automatically and cached in day_classification_cache.
  • Chronotype from a circular median of mid-sleep on free days — clock times treated as points on a 24 h circle via atan2 of summed sines and cosines, then unwrapped. Early < 6:00, late > 8:00. Social jetlag falls out of the same numbers.
  • Sleep debt with exponential decay — exp(−0.5 × dayIndex) over 14 days, capped at 20 h, bucketed low/moderate/high/critical, plus a payback-nights estimate.
Against myvitals: analytics/advanced.py:sleep_debt_hours is a flat 7-day sum of (user-typed target_h − actual) with no decay and no derived need; sleep_consistency_score is circular standard deviation only. Porting the derived-need idea needs no new ingest, is fully deterministic and server-side, and feeds the existing sleep coach and readiness score. It is the highest-value idea in this document that costs nothing but arithmetic.

The pattern underneath all of it

The analytic exists; the route does not

The single most repeated finding, across six of seven subsystems. cardio_summary and time_in_zone_for_activity are complete and reachable only from claude.py. tile_stats(db, day, …) and day_events(db, day, tz) are fully day-parameterised while their routes take no date. _wow_deltas computes exactly the period comparison four clients hand-roll. api/ai.py returns real goal progress the web throws away. Server-side work got written for the AI layer or one internal caller, was never given an HTTP surface, and a client then re-derived it — usually wrong. Auditing for "server functions with exactly one non-HTTP caller" would find more than any single subsystem review did.

Client-side re-derivation is where the parity rule is actually breaking

And parity_check.py cannot see it, because both files exist and both moved. Every verified divergence is a number computed in TypeScript or Kotlin: set prefill, HR zones, same-point-last-year, goal progress, units, session duration. The gate checks that paired files change together; it cannot check that they compute the same answer. In almost every case the structural fix is to delete client maths, not add a parity row.

Vocabulary drift between data and the code that consumes it

Verified four times over in the catalog alone: primary_muscle emits tokens MUSCLE_VOLUME_TARGETS does not contain; movement_pattern emits patterns no slot table names; mechanic disagrees with is_compound on 44 of 275 rows; force is on the wire and read by no Python. An alias map already exists twice — on the clients, for icons only. Display normalises; the maths does not. This is the one place SparkyFitness's actual mechanism, rather than just its shape, is worth copying.

Things granted, declared or shipped for nothing

The SpO2 permission is requested and its table has no writer. READ_RESTING_HEART_RATE is in the manifest and never requested. models.Workout is written every 15 minutes and read only by the CSV exporter. Equipment checkboxes for barbell, cable, kettlebell and bands gate a catalog slice that is empty. 45 correct exercise icons ship and are never referenced while 50 rows show another exercise's photo. createStrengthWorkout sits in client.ts with no caller. vitals_order has three readers and no writer. Individually each looks like an oversight; together they suggest a "declared but unconsumed" sweep would pay better than any single new feature.

Silent truncation at defaults nobody can see

Export defaults to end−90d and the UI sends no range. HealthConnectGateway caps at 100 pages × 5000 records. /query/last-sync looks at 4 of 10 tables. weekly_muscle_volume's if info is None: continue drops every imported exercise from the app's flagship analytic without a count. In each case the honest fix — surface the bound, or count what was dropped — is small, and much cheaper than the features built on top.
